# Тестовые данные для системы обработки заявок

## Обзор

Скрипт `scripts/populate_test_data.py` (и эквивалентный SQL-скрипт `scripts/populate_test_data.sql`) заполняют БД реалистичными демонстрационными данными для разработки и тестирования функциональности системы обработки заявок.

### История переходов (RequestHistory)

Каждая заявка со статусом, отличным от "Новая", имеет цепочку записей об изменении статуса:

- **Заявки 1-3**: только начальный статус "Новая"
- **Заявки 4-6**: Новая → В работе
- **Заявки 7-8**: Новая → В работе → На проверке
- **Заявка 9**: Новая → В работе → На проверке → Одобрена
- **Заявка 10**: Новая → В работе → На проверке → Одобрена → Завершена

## Использование

### 1. Способ: Python скрипт

```bash
python scripts/populate_test_data.py
```

Требует:
- Python 3.10+
- Установленный пакет request-system (`pip install -e .`)

Преимущества:
- Проверяет, что БД пуста перед вставкой
- Выводит детальное резюме операции

### 2. Способ: SQL-скрипт напрямую

```bash
sqlite3 request-system.db < scripts/populate_test_data.sql
```

Требует:
- sqlite3 в PATH

Преимущества:
- Не требует Python
- Быстро работает

### 3. Способ: PowerShell скрипт

```powershell
.\scripts\populate_test_data.ps1
```

Требует:
- PowerShell 5.1+
- sqlite3 в PATH

## Безопасность

**Оба скрипта проверяют, что БД пуста перед вставкой.** Это предотвращает случайное перезаписание существующих данных.

Если БД уже содержит данные, скрипт отменяется и выводит сообщение:

```
❌ Database already contains data. Aborting to prevent data loss.
To reset: delete the database file and reinitialize
```

### Полная переинициализация

1. Удалите БД:
   ```bash
   rm request-system.db
   ```

2. Запустите приложение (это создаст свежую БД с пустыми таблицами):
   ```bash
   python -m request_system list
   ```

3. Заполните тестовыми данными:
   ```bash
   python scripts/populate_test_data.py
   ```

## Проверка с помощью SQL

Прямой запрос к БД:

```sql
-- Количество данных каждого типа
SELECT 
  (SELECT COUNT(*) FROM Users) as users,
  (SELECT COUNT(*) FROM Categories) as categories,
  (SELECT COUNT(*) FROM Statuses) as statuses,
  (SELECT COUNT(*) FROM Requests) as requests,
  (SELECT COUNT(*) FROM RequestHistory) as history;

-- Распределение заявок по статусам
SELECT 
  s.name,
  COUNT(*) as count
FROM Requests r
JOIN (SELECT request_id, MAX(history_id) as latest FROM RequestHistory GROUP BY request_id) l 
  ON r.request_id = l.request_id
JOIN RequestHistory rh ON l.latest = rh.history_id
JOIN Statuses s ON rh.new_status_id = s.status_id
GROUP BY s.name
ORDER BY s.status_id;

-- История заявки 10 (самая сложная)
SELECT 
  rh.history_id,
  rh.request_id,
  (SELECT name FROM Users WHERE user_id = rh.actor_user_id) as actor,
  (SELECT name FROM Statuses WHERE status_id = rh.previous_status_id) as from_status,
  (SELECT name FROM Statuses WHERE status_id = rh.new_status_id) as to_status,
  rh.occurred_at,
  rh.explanation
FROM RequestHistory rh
WHERE rh.request_id = 10
ORDER BY rh.occurred_at;
```

## Особенности

1. **Уникальные номера заявок**: REQ-001 .. REQ-010
2. **Реалистичные описания**: 50-200 символов на русском
3. **Хронологичные временные метки**: заявки созданы с интервалом в 1 день
4. **Логичные цепочки статусов**: переходы между статусами соответствуют бизнес-процессу
5. **Разные акторы**: разные пользователи изменяют статусы
6. **Объяснения**: каждый переход имеет объяснение

## Примечания

- Скрипты используют `ON CONFLICT DO NOTHING` для идемпотентности — можно запускать несколько раз без ошибок
- Начальные статусы заявок всегда "Новая" (требование системы)
- Пользователи не имеют назначенных ролей — это можно добавить отдельно
- Тестовые данные включены в систему контроля версий для воспроизводимости среды разработки
