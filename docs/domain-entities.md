# Сущности предметной области

Концептуальная модель системы обработки заявок. Она описывает значимые для процесса объекты и связи между ними, а не структуру хранения данных.

## Сущности

| Сущность | Назначение и основные сведения |
|---|---|
| **Пользователь** | Участник с единой учётной записью, именем и контактными данными. Один и тот же пользователь может выступать в разных ролях и участвовать в разных заявках. |
| **Роль** | Набор разрешённых действий: заявитель, оператор, исполнитель или контролёр результата. Администратор — необязательная роль; её наличие не создаёт отдельный тип пользователя и не даёт права принимать результат вместо контролёра. |
| **Заявка** | Обращение о работе или услуге: уникальный номер, описание, заявитель, категория, приоритет, дата регистрации и текущий статус. Категорию может уточнить оператор; приоритет указывает оператор. |
| **Категория** | Классификация работы или услуги. Одна категория может относиться к нескольким заявкам. |
| **Статус** | Элемент справочника этапов обработки, например: новая, на проверке, ожидает уточнения, назначена, в работе, на приёмке, на доработке, закрыта или отменена. Само наличие статуса в справочнике не означает, что какая-либо заявка сейчас находится на этом этапе. |
| **Событие истории статусов** | Факт перехода конкретной заявки: предыдущий и новый статусы, автор, время и, если указано, пояснение. Для первоначального статуса предыдущего значения нет. События не заменяют текущий статус заявки. |
| **Назначение** | Факт назначения заявки конкретному исполнителю: заявка, исполнитель, назначивший пользователь, время начала и завершения, а при переназначении — причина. Каждое переназначение образует новую запись, а не стирает предыдущую. |
| **Комментарий** | Сообщение по заявке с текстом, автором, временем и признаком служебного комментария. В частности, комментариями могут быть запрос уточнения, ответ заявителя или пояснение о ходе работ. |
| **Предъявление результата** | Описание выполненной работы, переданное на проверку. Каждое предъявление связано с одной заявкой и одним автором-исполнителем; повторная передача после доработки сохраняется как отдельный факт. |
| **Решение о приёмке** | Результат проверки конкретного предъявления: принято или возвращено на доработку, контролёр, время и комментарий/причина. Решение относится к предъявлению результата, а не просто к текущему состоянию заявки. |

## Связи и кардинальности

| Связь | Кардинальность и смысл |
|---|---|
| Пользователь — Роль | Многие ко многим: у пользователя одна или несколько ролей; одна роль может быть назначена многим пользователям. Роли не создают отдельных копий пользователя. |
| Пользователь — Заявка (заявитель) | Один пользователь может создать много заявок; у каждой заявки ровно один заявитель. |
| Категория — Заявка | Одна категория может быть у многих заявок; у каждой заявки одна категория. |
| Статус — Заявка (текущий статус) | Один статус справочника может быть текущим у многих заявок; у каждой заявки ровно один текущий статус. |
| Заявка — Событие истории статусов | У заявки ноль или много событий; каждое событие относится ровно к одной заявке. Для события указаны ровно один новый статус и один автор; предыдущий статус может отсутствовать только при установке начального статуса. |
| Заявка — Назначение | У заявки ноль или много записей назначений; каждая запись относится ровно к одной заявке. В каждый момент времени у заявки не более одного действующего назначения. |
| Пользователь — Назначение | Пользователь может фигурировать во многих назначениях как исполнитель и отдельно как назначивший; у каждой записи назначения ровно один исполнитель и один назначивший пользователь. |
| Заявка — Комментарий | У заявки ноль или много комментариев; каждый комментарий относится ровно к одной заявке и имеет ровно одного автора-пользователя. Комментарии отображаются как отдельные события в истории заявки. |
| Заявка — Предъявление результата | У заявки ноль или много предъявлений; каждое предъявление относится ровно к одной заявке и имеет ровно одного автора-исполнителя. |
| Предъявление результата — Решение о приёмке | У предъявления может не быть решения до проверки либо может быть история решений; каждое решение относится ровно к одному предъявлению и имеет ровно одного автора-контролёра. |

Отдельная [ER-диаграмма таблиц](architecture/er-diagram.md) показывает поля, PK/FK и кардинальности логической схемы.

## Уточнения и допущения

- Текущий статус заявки — её актуальное состояние; история статусов хранит отдельные факты переходов. Аналогично, текущий исполнитель определяется действующим назначением, а прежние назначения сохраняются.
- История заявки объединяет для просмотра отдельные факты смены статуса, назначения, комментарии и решения о приёмке; отдельная сущность «общая запись истории» не требуется.
- Формальное принятие результата или возврат на доработку фиксирует контролёр. Упомянутое в описании роли заявителя подтверждение выполнения или сообщение о проблеме концептуально считается обратной связью/комментарием, а не решением о приёмке, чтобы не смешивать полномочия и не позволять заявителю закрывать заявку в обход контролёра.
- Вложения допускаются требованиями как сопровождающие материалы, но не обязательны; они показаны в отдельной диаграмме как необязательная связь с заявкой. Отдельная оценка результата требованиями не задана и не моделируется.
- Уведомления являются требуемым поведением системы, но отдельная сущность для их хранения в требованиях не установлена, поэтому в концептуальную модель не включена.
- Точные значения приоритета, правила переходов и полный состав полномочий определяются регламентом; отдельный справочник приоритетов требованиями не установлен.
