# Система обработки заявок

Учебный проект информационной системы для централизованной регистрации, распределения, выполнения и контроля заявок на работы или услуги.

## Текущее состояние

Проект находится на этапе каркаса. Сейчас реализована только CLI-заглушка, которая выводит сообщение о готовности. Перечисленные ниже функции являются целевыми и пока не реализованы.

## Назначение

Система должна помогать заявителям отслеживать обращения, операторам — проверять и назначать заявки, исполнителям — фиксировать ход работы и результат, а контролёрам — принимать результат или возвращать его на доработку.

## Планируемые функции

- создание заявок с описанием и категорией, просмотр статуса и истории;
- проверка заявок, запрос уточнений и назначение исполнителей;
- фиксация хода выполнения и передача результата на проверку;
- приёмка результата или возврат на доработку;
- уведомления участников и разграничение доступа по ролям.

Подробные требования, роли, сущности и критерии приёмки описаны в [техническом задании](docs/TZ.md).

## Архитектура

Целевое устройство — четыре слоя. Модули предметной области развиваются по реальным сценариям, а не обязаны иметь отдельный контроллер, сервис и репозиторий каждый.

```text
Вызовы во время выполнения:
presentation/controller -> service -> repository implementation (port) -> database

Зависимости исходного кода:
presentation -> service -> repository contract <- infrastructure adapter
```

- `presentation` — интерфейс и адаптеры ввода/вывода; преобразуют входные данные и вызывают сценарии. Не содержат бизнес-правил и не обращаются к хранилищу напрямую.
- `services` — прикладные сценарии и бизнес-правила; зависят от контрактов репозиториев, но не от интерфейса или конкретной инфраструктуры.
- `repositories` — контракты чтения/сохранения, необходимые сценариям. Они не содержат пользовательский интерфейс и бизнес-решения.
- `infrastructure` — реализации контрактов, подключения и детали хранения. Адаптеры могут зависеть от контрактов репозиториев, но прикладные слои не должны зависеть от конкретных адаптеров.

Стрелка вызова во время выполнения и направление зависимости исходного кода — не одно и то же: сервис вызывает порт репозитория, а инфраструктурная реализация предоставляет этот порт. Так сервисы остаются тестируемыми с подменным репозиторием и не привязаны к СУБД. Конкретная СУБД не выбрана.

Сейчас в коде есть только пакеты-заготовки слоёв; бизнес-функции и адаптер хранения не реализованы. [Слоистая архитектура](docs/architecture/architecture.puml) и [диаграмма компонентов](docs/architecture/components.puml) показывают целевую схему.

## Структура исходного кода

```text
src/request_system/
├── __main__.py          # запуск приложения
├── presentation/        # CLI и другие адаптеры взаимодействия
├── services/            # сценарии и бизнес-правила
├── repositories/        # контракты доступа к данным
└── infrastructure/      # реализации и интеграции
    └── database/
tests/                    # автоматические проверки, включая границы слоёв
```

Добавляйте компоненты вместе с вертикальными пользовательскими сценариями. Не создавайте заранее пустые классы или одинаковые репозитории на каждую сущность: например, статусы могут быть правилами переходов заявки, а комментарии — частью её сценария, пока им не нужна самостоятельная ответственность.

## Разработка и проверка

Создайте и активируйте виртуальное окружение, затем установите проект:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e .
```

Запустить приложение и тесты можно командами:

```powershell
python -m request_system
python -m unittest discover -s tests -v
```
